1. Purpose

This document describes how a venue screen (smart TV, Fire Stick browser, kiosk PC) shows a live match scoreboard that updates in real time when a scorer uses the Sportza web app. The scoreboard page is intentionally not behind Auth0: anyone who can open the URL can subscribe to public match updates for that match id.

Implementation references: API socket bootstrap apps/api/src/lib/socket.ts, HTTP server attachment apps/api/src/index.ts, match emits apps/api/src/routes/matches.ts, TV page apps/web/src/pages/matches/Scoreboard.tsx, client hook apps/web/src/hooks/useMatchSocket.ts.

2. System overview

The match creator (authenticated in the app) sends score and event updates via REST. The API persists to MySQL and broadcasts to every Socket.io client in the match room match:<id>. The scoreboard page loads once over REST for initial teams and scores, then keeps the UI in sync via WebSocket events.

  • Scorer app — Logged-in user; calls PUT /api/matches/:id/score, POST /api/matches/:id/events, PUT /api/matches/:id/status, etc.
  • API server — Single process: Express REST + Socket.io on the same TCP port as HTTP (upgrade to WebSocket).
  • Scoreboard page — Static SPA route /scoreboard/:matchId; first request loads HTML/JS from the web app origin; REST and socket URLs come from VITE_API_URL (socket base URL strips the /api suffix in the client hook).

4. Room model

Socket.io rooms isolate broadcasts per match:

  • Room name: match:<matchId> (numeric id as string).
  • After the WebSocket connects, the client emits match:join with the match id; the server joins the socket to that room.
  • Multiple displays can join the same room (several TVs, or TV plus a laptop). All receive the same match:score, match:event, and match:status payloads.
  • No authentication is required to connect or join: this is by design for kiosk-style displays. Treat the match id as a capability token; do not share the URL publicly if the match should stay private.
  • On disconnect or navigation away, the client emits match:leave and closes the socket.

5. Socket event reference

Event Direction Payload
match:join Client to server matchId number or string
match:joined Server to client matchId, room string
match:score Server to room matchId, scores object, winnerTeam, status
match:event Server to room matchId, event with id, team, eventType, eventValue, playerName, eventTimestamp
match:status Server to room matchId, status string
match:leave Client to server matchId

REST routes that trigger emits are defined in apps/api/src/routes/matches.ts (score update, add event, status update, start, complete).

6. Putting the scoreboard on a TV

  1. Deploy or run the web app so it has a stable HTTPS URL (production) or HTTP URL (local demo).
  2. In the app, open the match detail page and note the match id (or use the Scoreboard link which opens /scoreboard/<matchId> in a new tab).
  3. On the TV or stick, open a browser and navigate to:
    https://<your-web-host>/scoreboard/<matchId>
  4. Ensure the TV can reach both the web origin (for the SPA) and the API host configured in VITE_API_URL (for REST and Socket.io). In dev, that is often http://localhost:5000/api for REST and http://localhost:5000 for the socket; a TV on the same LAN must use the PC LAN IP instead of localhost.
  5. Works in any modern browser on the TV or stick: Chrome, Firefox, Samsung Smart TV browser, Amazon Fire TV Silk, etc.
  6. Use the browser or OS fullscreen mode (e.g. F11 on desktop, or the TV full-screen control) for a clean display.
  7. The Socket.io client retries automatically if Wi-Fi drops (up to 10 attempts with backoff).

7. Transports: WebSocket and fallback

Both server and client enable websocket and polling. Socket.io tries a WebSocket upgrade first; if a corporate firewall or proxy blocks WebSockets, it falls back to HTTP long-polling on the same origin without code changes on the scoreboard page.

8. CORS and production checklist

  • API CORS CLIENT_ORIGIN should list the web app origin. Socket.io uses the same CORS settings for the initial handshake.
  • If the scoreboard is opened from a file URL or another origin, verify browser console for CORS or mixed-content errors; align all URLs to HTTPS in production.
  • Future hardening options (not implemented in baseline): short-lived display tokens, venue-bound pairing codes, or signed URLs for the scoreboard route.
