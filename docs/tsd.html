2. Purpose of the Document

This Technical Specification Document (TSD) describes the technical design of Sportza (sports venue booking & tournament platform). Intended for:

  • Development teams — Implementing the system (backend API, frontend app, real-time scoring)
  • Architects and reviewers — Validating technology choices, data model, integration approach
  • QA and DevOps — Test strategy, deployment, environment configuration

The TSD bridges business and functional requirements (BRD, FRD) with implementation. It references them and adds technical detail.

3. Scope Overview

3.1 In-Scope

  • Web application (React) — Mobile-first UI; bottom nav (Home | Bookings | Open Play | Stats | Profile); booking flow, open play, stats, leaderboard, venue/trainer discovery, ratings & reviews
  • REST API (Node.js/Express) — Auth, sports, venues, bookings, payments, open plays, matches, tournaments, batches, trainers, stats, reports
  • Real-time scoring — Socket.io for live match score updates
  • Payment integration — Razorpay; commission and net amounts per booking and batch payment
  • Data persistence — MySQL (Prisma); booking state logic; monthly reports
  • Authentication — Auth0 (Google SSO, Email OTP, Magic Link); role-based access
  • Booking state engine — T-30 checkpoint; status matrix; payment-priority confirmation
  • Scheduled jobs — Open-play confirmation at T-30

3.2 Out-of-Scope

  • Native iOS/Android apps (responsive web; API supports future native clients)
  • Detailed NFR document (separate deliverable)
  • Third-party venue management systems integration
  • Automated payout execution (reports only; payouts manual or future phase)

4. System Overview

4.1 Business Context

The platform serves Players, Venue owners, Trainers, and Admin. Revenue model: platform commission % on venue bookings and batch fee payments; settled month-wise.

5. Architecture Overview

5.1 Logical Architecture

Client Layer (React SPA): Auth (Auth0), Home/Venues/Matches/Train/Profile, Booking Flow, Discovery & Reviews, Socket.io Client ↓ HTTPS / WSS API Layer (Node.js/Express): REST endpoints, Auth0 JWT & Role Checks, Socket.io Server ↓ Business & Data Layer: Booking State Engine, Open-Play Job, Payment/Commission Calc, Match Scoring, Prisma Models ↓ Data Store: MySQL

Layer summary: Client (UI, auth, booking, discovery, live match); API (REST, JWT, Socket.io); Business (state logic, commission, validation); Data Store (MySQL).

9. Calculation & Rule Engine

9.1 Calculation Flow

Booking: Resolve rate from Venue; apply min duration; subtotal = rate × hours; gstAmount = subtotal × gstRate; totalAmount = subtotal + gst + addOns; platformCommissionAmount = (subtotal + gst) × commissionPercent (add-ons excluded); venueNetAmount = totalAmount − commission.

Batch payment: platformCommissionAmount = amount × batch.commissionPercent/100; trainerNetAmount = amount − commission.

T-30: If paid % ≥ 50% (and open play full) → confirmed; else cancelled.

9.2 Key Formulas

FormulaDescription
subtotalΣ (rate × hours); minus batch discount if applicable
gstAmountsubtotal × (venue.gstRate / 100)
totalAmountsubtotal + gstAmount + Σ addOn amounts
platformCommissionAmount(subtotal + gstAmount) × (venue.commissionPercent / 100)
venueNetAmounttotalAmount − platformCommissionAmount
Paid % (split)(Σ splitPayments paid) / totalAmount × 100

9.3 Validation Rules

Booking: facilityId and facilityName required; slot available; split sums to total; batch discount only if batch.venue = booking.venue. Trainer review: only if PlayerBatchReview exists. Match score: validated by scoreType. Tournament: knockout requires team count power of 2.

10. User Management & Security

10.1 Authentication & Authorization

Authentication: Auth0 (Google SSO, Email OTP via Redis, Magic Link); JWT in Authorization: Bearer; Auth0 middleware verifies tokens.

Authorization: Role-based (player, venue_owner, trainer, admin). Venue owner only own venues; trainer only own batches; tournament creator only own tournament.

10.2 Data Security

HTTPS in production; WSS for Socket.io. Secrets in env vars. Payment instruments not stored (Razorpay). Input validation via Zod; sanitization for XSS/injection.

12. Deployment & Release Management

Build: pnpm build (Turborepo). Web: Vite; API: TypeScript build.

Environment: PORT, DATABASE_URL, REDIS_URL, AUTH0_*, CLIENT_ORIGIN; Razorpay keys.

Process: Single Node process for API + Socket.io; static client from apps/web/dist.

Docker: docker-compose.yml — MySQL, Redis, API, Web. docker-compose up for full stack.
